# 我第一次做微服务：用一个真实项目，把「从单体到微服务」讲明白

> **摘要**：我一直以为"微服务"无非就是"把代码拆成好几个项目"，直到我把自己那套高校管理系统从一个大 WAR 包，拆成 8 个能独立部署的服务，才发现真正的难点根本不是"拆"，而是**拆开之后冒出来的一堆新问题**——服务怎么互相找到？怎么调用？外部请求怎么进来？一个服务挂了怎么办？这篇文章记的是我理清这些问题的过程，用我自己的项目当标本。如果你也卡在"知道要拆，但不知道拆完会发生什么"，希望它有用。

---

## 一、引子：我那套系统是怎么"长大"的

最开始，我整个系统就是一个 WAR 包——**一个进程，什么都装在里面**：活动、成员、项目、奖项、群聊、AI 助手，还有前端 JSP，全在一个 `software-group.war` 里，跑在一个 Tomcat 上。

这就是**单体应用（Monolith）**。小的时候很爽：一个包部署，改代码打一次包就行。但它会长大，长大就疼：

| 疼点 | 具体表现 |
|---|---|
| **改一处，全量重启** | 只想改个 AI 助手的回复格式，整个系统得停几秒重启 |
| **一崩全崩** | 群聊模块一个内存泄漏，整个 Tomcat OOM，所有人都用不了 |
| **扩容只能整体扩** | 活动页流量大，我也只能把**整个 WAR** 多复制几份——浪费 |
| **技术栈被锁死** | 全系统只能 Java + JSP，AI 那部分想用 Python 都没法接 |
| **团队互相踩脚** | 几个人改同一个 WAR，代码冲突、上线打架 |

**微服务要干的，就是把"一个大食堂"拆成"美食广场"**：每家店（服务）自己进货、自己开业、自己雇人——谁家火了就多开几家（单独扩容），谁家倒闭了别的店照常营业（故障隔离）。

---

## 二、微服务到底是什么

> **微服务 = 把一个大的业务系统，按业务边界拆成一组小的、能独立开发、独立部署、独立运行的"服务"，服务之间通过网络互相调用。**

但有个**极其重要的前提**：小，不等于微服务。**"把代码拆成好几个文件"不是微服务。** 真正的微服务必须具备：

- **独立部署**：每个服务是一个独立的进程/容器（我项目里就是 `user-service` 容器、`file-service` 容器……）。
- **围绕业务划分**（不是按技术划分）：不是"所有 Controller 一个服务、所有 DAO 一个服务"，而是"用户相关的一个服务、文件相关的一个服务"。
- **通过网络通信**：服务之间不再是方法调用，而是 HTTP/RPC 调用。
- **去中心化数据**：理想情况每个服务管自己的数据库。

---

## 三、最重要的一课：服务分层 ≠ 微服务

这是像我第一次做时最容易搞混的地方，必须先说清楚。**服务分层**和 **API 化**，跟微服务**不是一回事**，它们是**两个方向**：

```
                     服务分层（纵向切）       微服务（横向切）

   ┌─────────────────────┐              ┌──────────┬──────────┐
   │ Servlet 层           │              │ 用户服务  │ 文件服务  │
   ├─────────────────────┤              │(含三层)  │(含三层)  │
   │ Service 层           │   ────▶      ├──────────┼──────────┤
   ├─────────────────────┤              │ 活动服务  │ 奖项服务  │
   │ DAO 层               │              │(含三层)  │(含三层)  │
   └─────────────────────┘              └──────────┴──────────┘
    一个进程内，按"职责"分层              多个进程，按"业务"切分
```

- **服务分层**：在**一个进程里**，把代码按职责竖着切成 Servlet / Service / DAO。
- **API 化**：在**一个进程里**，给 Service 开标准的数据出入口。
- **微服务**：把这些切好的业务，**横着切成多个独立进程**。

**关键**：微服务里的**每一个服务，内部照样是三层**。看我项目里的 `user-service`：

```
user-service/
├── controller/   AuthController, MemberController     ← 相当于 API 层
├── service/      AuthService, MemberService           ← 业务层
├── dao/          UserDAO, MemberProfileDAO, ...        ← 数据层
├── feign/        FileFeignClient                       ← 微服务新增：调用别的服务
└── UserServiceApplication.java                          ← 启动类
```

**所以微服务不是"另一种写法"，而是"你把分层 + API 化做得足够干净之后，自然能切出去的结果"。** 前面两步没白学——没有干净的 Service 边界和 API 边界，根本切不出微服务。

## 四、我项目的微服务全景

拆完之后，是一个 **父 POM + 1 个共享模块 + 8 个微服务** 的结构：

```
software-group-microservices（父 POM，统一版本管理）
├── common/                     ← 所有服务共享：Result、JwtUtil、BusinessException…
├── file-service          :8081   文件上传/下载/MinIO
├── user-service          :8082   认证登录、JWT 签发、成员档案
├── activity-service      :8084   活动、考勤、学习记录
├── project-award-service :8085   项目、奖项
├── monitor-service       :8086   问题反馈、操作日志
├── content-service       :8087   群聊、新闻
├── hr-service            :8089   招新、简历
└── ai-service            :8094   AI 助手
```

父 POM 里还给服务排了"梯队"（这个顺序是编译依赖顺序，很讲究）：

```xml
<module>common</module>            <!-- 最先 -->
<module>file-service</module>      <!-- 基础服务 -->
<module>user-service</module>      <!-- 依赖 file-service -->
...
```

**为什么这么排？** 因为 `user-service` 要调用 `file-service`（上传头像），所以它得排在后面、依赖它。

## 五、微服务带来的 6 个新问题（以及我是怎么解的）

拆开很爽，但**"拆开"本身会制造出一堆单体时代不存在的问题**。这才是微服务真正的难点，也是你必须学会的东西。

### 问题 ①：服务怎么互相"找到"？——服务注册与发现（Nacos）

单体时代，调一个方法就是 `userService.login()`，近在咫尺。

**拆开之后**：`user-service` 是**另一个进程、另一个容器**，IP 还不固定（容器重启 IP 就变）。它想找 `file-service`，怎么找？

**解法：服务注册中心（我项目用 Nacos）**。

- 每个服务**启动时**去 Nacos **报到**："我是 `user-service`，我在 8082，我的 IP 是 172.x.x.x"。
- 别的服务要找它，**问 Nacos**："`file-service` 在哪？" → Nacos 回答。

看 `user-service` 的报到信息（`bootstrap.yml`）：

```yaml
spring:
  application:
    name: user-service          # ← 我在注册中心的"名字"
  cloud:
    nacos:
      server-addr: ${NACOS_HOST:nacos}:${NACOS_PORT:8848}   # ← 注册中心地址
      discovery:
        namespace: public
        group: DEFAULT_GROUP
```

启动类上的注解就是"报到开关"：

```java
@EnableDiscoveryClient          // ← 我也要注册到注册中心
@SpringBootApplication(...)
public class UserServiceApplication { ... }
```

**核心理解**：注册中心就是**服务的通讯录**。服务名（`user-service`）就是它在通讯录里的名字。

### 问题 ②：服务怎么互相"调用"？——OpenFeign

找到之后，调用也不能再是方法调用，得发 HTTP 请求。手写 HttpClient 太麻烦，我项目用 **OpenFeign**——**你只写一个接口，它帮你生成实现**：

```java
@FeignClient(name = "file-service", path = "/api/files")   // ← 我要调 file-service
public interface FileFeignClient {

    @GetMapping("/{fileId}")
    Result getFileInfo(@PathVariable("fileId") Integer fileId);

    @PostMapping(value = "/upload", consumes = MediaType.MULTIPART_FORM_DATA_VALUE)
    Result uploadFile(@RequestPart("file") MultipartFile file, ...);
}
```

**我没有写任何实现类**——Spring Cloud 在启动时**自动生成**一个代理：我调 `fileFeignClient.getFileInfo(5)`，它就变成 `GET http://file-service:8081/api/files/5` 发出去。

> **这里藏着一个漂亮的细节**：Feign 里的 `name = "file-service"` **不是 IP**，是**服务名**。Feign 会先问 Nacos"`file-service` 在哪"，拿到真实 IP 再发请求。**服务名当域名用**——这跟 Docker 篇讲的"容器名当域名"是同一个思想。

### 问题 ③：外部请求怎么进来？——API 网关

浏览器只知道一个地址（你的服务器），它不知道你有 8 个服务、各自什么端口。总不能让用户记住 `:8081`、`:8082`……

**解法：一个统一入口，按 URL 把请求转发给对应服务。** 我项目用的是 **nginx 网关**：

```nginx
location /api/users/ {
    set $user_service user-service:8082;      # 服务名:端口
    proxy_pass http://$user_service;
}
location /api/files/ {
    set $file_service file-service:8081;
    proxy_pass http://$file_service;
}
location /api/activities/ {
    set $activity_service activity-service:8084;
    proxy_pass http://$activity_service;
}
```

**于是外部世界只看到 `http://你的域名/api/xxx`**，nginx 在背后按 `/api/` 前缀把请求分发给不同服务。**API 化的 URL 边界，到这里变成了微服务的物理边界**——这就是为什么 API 化那么重要。

### 问题 ④：一个服务挂了怎么办？——熔断降级（Sentinel）

拆开后，调用链变长了：`user-service` 调 `file-service`，如果 `file-service` 卡住/挂了，`user-service` 的线程会全被拖死，然后连它也崩——**这就是"雪崩"**。

**解法：熔断器（我项目用 Sentinel）**。依赖里有 `spring-cloud-starter-alibaba-sentinel`，配置里一句开关：

```yaml
spring.cloud.sentinel:
  enabled: true
```

它的作用：当一个服务调用持续失败，**快速失败**（不再傻等），或者**降级**（返回一个兜底结果），**防止一个服务的故障传染给整个系统**。

### 问题 ⑤：配置怎么管？——配置中心 + 环境变量

8 个服务，每个都有自己的 `application.yml`。改一个数据库地址，难道要改 8 个文件、重新打包 8 次？

**解法**：我项目用了两层——
- **环境变量注入**（`${DB_HOST:mysql}` 这种）：同一份镜像，换套环境变量就连不同的库（跟 Docker 篇讲的完全一致）。
- **Nacos 配置中心**（`bootstrap.yml` 里配了 `config`）：配置可以集中放在 Nacos，服务启动时去拉。

### 问题 ⑥：一个请求跨了好几个服务，出错怎么排查？——日志/链路追踪

单体时代一个堆栈就能看完；微服务里一个请求可能跨 3 个服务，日志散在 3 个容器里。我目前的解法是**统一日志格式 + 统一异常处理**，更完善的链路追踪（如 SkyWalking）是下一步。

## 六、走一遍跨服务调用链：用户上传头像

这是最能体现微服务"协作"的一条链：

```
浏览器: POST /api/members/5/avatar   （带文件 + JWT）
   │
   ▼  nginx 网关：/api/members/ → user-service:8082
   │
   ▼  user-service.MemberController
   │      JwtAuthFilter 验 JWT，把用户信息塞进 X-User-Id 头
   │
   ▼  user-service 的 Service 层
   │      要做的事：把文件存起来 → 但"存文件"不是我的活
   │
   ▼  FileFeignClient.uploadFile(...)        ← 跨服务调用！
   │      （Feign 问 Nacos：file-service 在哪？→ 172.x.x.x:8081）
   │
   ▼  file-service.FileController
   │      FileService → 存 MinIO → 写 file_storage 表
   │
   ▲  返回 Result{data: {fileId: 88}}
   │
   ▼  user-service 拿到 fileId，更新 member_profile.avatar_file_id
   ▲
   ▼  返回 JSON 给浏览器
```

**看明白了吗？** `user-service` 处理"改头像"这个业务，但**它不碰文件存储**——那是 `file-service` 的专业。两个服务**各司其职、通过 API 协作**。这正是"按业务边界拆分"的威力。

## 七、几个关键机制拆解

### 1. `common` 模块 —— 只放"所有服务都必须共享"的东西

8 个服务都需要统一返回 `{code, message, data}`、都需要 JWT 工具、都需要统一异常处理。这些不能每个服务复制一份，于是抽成 `common`：

```
common/src/main/java/com/softwaregroup/common/
├── util/Result.java                      ← 统一响应体（跟 API 化那篇一模一样）
├── util/JwtUtil.java                     ← 签发/校验 JWT
├── exception/BusinessException.java      ← 业务异常
├── exception/GlobalExceptionHandler.java ← 统一异常 → JSON
├── dto/PageRequest.java, PageResult.java
```

**这是微服务的一个通用原则**：跨服务的"契约"（响应格式、认证方式、异常约定）要共享；**业务逻辑绝不共享**（共享业务逻辑 = 服务间隐式耦合，就白拆了）。

### 2. `GlobalExceptionHandler` —— 每个服务自动"长得一样"

用 `@RestControllerAdvice` 全局拦截异常，所有服务的错误响应格式统一：

```java
@RestControllerAdvice
public class GlobalExceptionHandler {
    @ExceptionHandler(BusinessException.class)
    public Result handleBusinessException(BusinessException e) {
        return Result.error(e.getCode(), e.getMessage());   // → {code, message, data}
    }
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public Result handleValidationException(...) { ... }     // 参数校验失败
}
```

**它在 `common` 里，8 个服务一引入就都有了。** 这就是"标准化"。

### 3. 每个服务都是"Spring Boot 应用 + 一套注解"

跟 `user-service` 启动类一样：

```java
@SpringBootApplication(exclude = {SecurityAutoConfiguration.class})
@EnableDiscoveryClient                                  // 注册到 Nacos
@EnableFeignClients(basePackages = "...user.feign")     // 开启 Feign 调用
@ComponentScan(basePackages = {"...user", "...common"})  // 扫到 common 的组件
public class UserServiceApplication { ... }
```

### 4. nginx 的"变量 + resolver" —— 动态解析服务名

注意到 nginx 里是 `set $file_service file-service:8081;` 然后 `proxy_pass http://$file_service;`，而不是直接写死 IP。**这是故意的**：用了变量，nginx 就会在**每次请求时**通过 Docker 内置 DNS 解析 `file-service`，而不是启动时解析一次。这样某个服务容器重启换了 IP，nginx 也照样能找到它。

## 八、一个诚实的观察：数据库怎么分？

严格意义上的微服务，**每个服务应该有自己独立的数据库**（"去中心化数据"）。但我这个项目做了一个**务实的折中**——**共享同一个 MySQL 实例，但给每个服务单独的数据库账号，并限制它只能访问自己的表**：

```sql
-- file-service：只访问文件相关表
CREATE USER 'file_svc'@'%' IDENTIFIED BY '...';
-- user-service：访问用户、成员档案、管理员档案相关表
CREATE USER 'user_svc'@'%' IDENTIFIED BY '...';
-- activity-service：访问活动、考勤、学习相关表
CREATE USER 'activity_svc'@'%' IDENTIFIED BY '...';
...
```

**为什么这么干？** 因为要跟旧的单体 WAR **共用同一套数据**（迁移期不能把 45 张表拆得七零八落）。这是**"从单体迁移到微服务"最常见、也最务实的中间形态**。

**你要知道的两面**：

- **好**：不用改数据、旧系统和新服务能并行跑、迁移风险小。
- **代价**：服务间的数据边界还是"软"的（靠账号权限约束，不靠物理隔离），将来如果要独立扩缩容或换库，还得再拆一次。

> **学微服务一定要记住这点**：教科书版微服务（独立库、独立部署、全自动）和现实版（共享库、过渡期、逐步迁）**往往不是一个东西**。能识别"我现在处在哪个阶段、这个折中的代价是什么"，比背概念重要得多。

## 九、动手：微服务的开发与运行标准动作

### 本地/服务器怎么跑起来

我项目用 Docker Compose 一条命令拉起 16 个容器，其中 8 个是微服务：

```bash
docker compose up -d                      # 全栈启动
docker compose ps                          # 看哪些在跑
docker compose logs -f user-service        # 盯某个服务的日志
```

### 加一个新接口的标准动作

| 步骤 | 做什么 | 在哪 |
|---|---|---|
| 1 | 确定**归哪个服务**（按业务边界） | 选模块 |
| 2 | 写 **Controller**（薄，只转发） | `xxx-service/controller/` |
| 3 | 写 **Service**（业务逻辑） | `xxx-service/service/` |
| 4 | 写 **DAO**（SQL） | `xxx-service/dao/` |
| 5 | 需要调别的服务 → 写 **Feign 客户端** | `xxx-service/feign/` |
| 6 | 在 **nginx** 补路由（如果 URL 前缀是新的） | `nginx/nginx.conf` |
| 7 | 写测试 | `xxx-service/src/test/` |

**关键判断**：**这个功能"属于谁"？** 属于自己 → 自己实现；属于别人 → 用 Feign 调。**一旦发现两个服务要共享大量业务逻辑，说明边界切错了，该重新划分。**

## 十、我脑子里的那张微服务地图

```
   外部世界（浏览器/小程序）
        │  http://域名/api/xxx
        ▼
   ┌─────────────────────────┐
   │  API 网关（nginx）        │  按 /api/ 前缀分发
   └───────────┬─────────────┘
        ┌──────┴──────┬─────────────┐
        ▼             ▼             ▼
   user-service   file-service  activity-service  ...（8 个独立进程）
   ┌──────────┐  ┌──────────┐   ┌──────────┐
   │Controller│  │Controller│   │Controller│
   │ Service  │  │ Service  │   │ Service  │    ← 每个服务内部还是三层
   │  DAO     │  │  DAO     │   │  DAO     │
   └────┬─────┘  └────┬─────┘   └────┬─────┘
        │             │             │
        └──────┬──────┴──────┬──────┘
               ▼             ▼
       ┌────────────┐  ┌────────────┐
       │ Nacos 注册  │  │ MySQL/Redis│
       │ 中心(通讯录)│  │  RabbitMQ  │
       └────────────┘  │  MinIO     │
        ↑ 服务启动报到   └────────────┘
        ↑ 服务间调用前先查

   服务间调用：Feign（服务名当域名）  →  查 Nacos 拿 IP
   故障防护：Sentinel 熔断    统一契约：common 模块（Result/JWT/异常）
```

**我现在的理解浓缩成三句话**：

1. **微服务 = 把单体按业务边界横切成独立进程**；它和"服务分层（纵向切职责）"是**两个正交的方向**，每个微服务内部照样是三层。
2. **拆开就产生新问题**：找不到（→ 注册中心）、调不通（→ Feign）、进不来（→ 网关）、挂了传染（→ 熔断）——**微服务的难点不在"拆"，而在"拆开之后怎么协作"**。
3. **注册中心是通讯录，服务名就是域名**；网关（nginx）是唯一入口、按 API 前缀分发——**所以 API 化的边界，就是今天微服务的边界**。

拿到一个新需求，我现在会问三个问题：

- 这块业务**该属于哪个服务**？（按业务边界，不按技术）
- 它**需要调别的服务吗**？（需要 → 写 Feign 客户端）
- 这个功能**要不要在网关补路由**？（URL 前缀是新的 → nginx 加 location）

---

## 十一、收尾：四级台阶

我这一路摸索下来，其实正好是**同一个系统演进的四级台阶**：

```
① Docker      —— 怎么把服务装进盒子、编排起来跑     （运行环境）
② 服务分层    —— 盒子里的代码怎么按职责分成三层       （代码结构）
③ API 化      —— 分层的 Service 怎么开标准数据出口    （对外契约）
④ 微服务      —— 把干净的 API 边界切成独立进程        （部署形态）
```

**一条线串到底**：Docker 让服务能"跑起来"，服务分层让代码"理得顺"，API 化让边界"说得清"，微服务让它们"各立门户又互相协作"。**没有前三步，第四步就是空中楼阁。**

---

*如果你也是第一次做微服务：别一上来就想着"我要拆成几个服务"。先回头看看，你系统里的 Service 边界、API 边界清不清晰——边界清晰，拆是水到渠成；边界糊涂，拆了只会更乱。微服务这件事，考验的其实是你对业务的理解，而不是对框架的熟悉。*
