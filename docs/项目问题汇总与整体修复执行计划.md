## 4.1 认证与授权问题

### SEC-01：公开注册接口可以创建管理员（P0）（已修复）

**确认情况**

- `/api/users/register` 无需登录。
- 注册请求允许客户端提交 `ADMIN`、`MEMBER`、`TEACHER`。
- 服务端直接保存客户端提交的角色并签发 JWT。

**影响**

未登录用户可注册管理员账号并立即获得管理员身份。

**修复方案**

1. 公共注册服务端强制角色为 `MEMBER`。
2. 从公共注册 DTO 中移除角色字段，或完全忽略该字段。
3. 管理员、教师账号通过独立管理员接口创建。
4. 角色修改必须校验管理员权限并记录审计日志。
5. 上线前排查数据库中异常管理员账号。
6. 永久修复上线前，在 Nginx 临时禁止外部访问 `POST /api/users/register`。

**实施与验证记录（2026-11-11）**

- 已在本地移除公开注册 DTO 的角色字段，并显式忽略旧客户端传来的 `role`；`AuthService.register()` 服务端固定写入 `MEMBER`，响应用户资料和签发的 JWT 均使用该角色。
- 新增覆盖 `ADMIN`、`TEACHER` 和非法角色输入的反越权用例；登录、注册及成员管理相关回归测试通过。`mvn -o -pl user-service -am test`：common 6 项、user-service 42 项，合计 48 项通过，0 失败、0 错误。
- **标签范围：本地源码已修复；未部署生产。** 当前生产的旧 user-service 仍可能允许公开注册管理员。上线后需验证匿名请求不能获得管理员身份，并核查异常管理员账号；此前的临时 Nginx 阻断尚未实施。SEC-02 及其他问题未在本次修改。

### SEC-02：JWT 使用代码内固定密钥，环境变量实际无效（P0）（已修复）

**确认情况**

- `common` 模块的 JWT 工具使用固定常量签名。
- Docker Compose 虽然传入 `JWT_SECRET`，但当前公共 JWT 工具没有读取它。

**影响**

获得源码或固定密钥的人可以伪造任意用户、任意角色的 JWT。

**修复方案**

1. 将静态 JWT 工具重构为可注入的 `JwtService`。
2. 从环境变量或密钥管理系统加载生产密钥。
3. 生产环境缺少密钥时拒绝启动，禁止默认值回退。
4. 校验 `issuer`、`audience`、有效期和角色声明。
5. 增加密钥版本 `kid`，支持后续轮换。
6. 修复上线后立即生成新密钥，旧 Token 全部失效，用户重新登录。

**实施与验证记录（2026-11-11）**

**修复记录（2026-11-16，本地代码与迁移脚本）**

- 原过滤器直接采用请求中的 `X-Forwarded-For`、`Proxy-Client-IP` 等头；Nginx 原配置使用 `$proxy_add_x_forwarded_for`，会保留客户端伪造的链首值，且 WAR 的 8080 端口可直连，问题确实存在。
- Compose 中旧 WAR 通过 `AUDIT_TRUSTED_PROXY_HOSTS=nginx` 只信任同网络的 Nginx 服务地址。直连或 DNS 不可用时使用连接对端 IP，忽略所有转发头；仅当连接对端匹配 Nginx 地址时，接收格式正确的单个 `X-Real-IP`。无效值回退到连接对端 IP，不从客户端传来的 `X-Forwarded-For` 链挑选地址。
- Nginx 四条到 WAR 的代理路径均以 `$remote_addr` 覆盖 `X-Real-IP` 和 `X-Forwarded-For`，清除其他可伪造的代理身份头，并从访问日志中移除原始 `X-Forwarded-For`。当前部署按单跳 Nginx 处理；若 Windows 主机或其他代理位于 Nginx 前，需先核实可信上游再配置多跳链，不能直接信任其转发头。
- 新增可空 `proxy_ip`，`ip_address` 保存解析后的客户端 IP，`proxy_ip` 保存受信任代理的连接对端 IP；直连请求及历史行的 `proxy_ip` 为 `NULL`。迁移见 `migrations/20261116_aud03_operation_log_proxy_ip.sql`，须在 AUD-02 迁移之后、发布新 WAR 之前执行。
- 本地验证：IP 解析 5 项、过滤器 8 项、DAO 2 项、真实 HTTP 请求 1 项、monitor-service 映射 1 项、Nginx 头部策略 2 项、原路由策略 7 项及 Compose 配置检查均通过。生产 VM 未部署，Nginx 实际语法与容器间地址需在发布前用 VM 上的 `nginx -t` 和只读检查验证。

### AUD-05：操作日志可能记录敏感查询字符串（P1）（已修复）

**修复方案**

1. 禁止记录密码、Token、密钥、完整身份证明和敏感请求体。
2. 对 query string 使用字段白名单。
3. 对手机号、邮箱等信息脱敏。

**核实与实施（2026-11-16）**

- 核实发现：旧 WAR 的 `LoggingFilter` 对未命中固定描述的修改请求，把原始 `query string` 拼入 `operation_log.description`；命中描述时仍直接拼接请求参数 `id`。Nginx 访问日志原来记录完整 `$request`、Referer 和 User-Agent，也可能保存带密钥的 URL。

- Nginx 访问日志移除原始请求、Referer、User-Agent 和用户名；记录 Nginx 自行生成的请求 ID，同时只在上游 `X-Request-ID` 符合标准 UUID 格式时记录审计请求 ID，保留与 WAR 操作日志的跨层关联。新访问日志不再写入原始查询串。

## 八、回滚方案

### 8.1 应用回滚

1. 每次发布前保留上一版本镜像 tag 和 digest。
2. Compose 使用明确版本号，不使用不可追踪的 `latest`。
3. 单服务失败只回滚该服务和对应 Nginx 路由。
4. JWT 发布失败时回滚应用和密钥配置，但不得重新启用已泄露的固定密钥作为长期方案。

### 8.2 数据库回滚

1. 所有迁移先做逻辑备份。
2. 结构变更优先采用向后兼容方式：先加字段、双写、切换、最后删除旧字段。
3. 禁止在同一发布中直接删除仍被旧版本使用的字段。
4. 密码迁移保留短期双格式识别能力，但新写入只能使用安全哈希。

### 8.3 路由回滚

1. 每个微服务域单独维护 Nginx 路由切换记录。
2. 新微服务异常时切回已验证旧 WAR 接口。
3. 如果旧 WAR 契约不兼容，则返回明确 503，不返回虚假成功。
