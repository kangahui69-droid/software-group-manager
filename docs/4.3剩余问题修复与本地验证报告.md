## 整体完成前仍需执行

1. 在生产库已验证备份后，确认 `ai_conversation.session_id` 无重复并执行 [MIG-03 唯一索引迁移](../migrations/manual/MIG-03_ai_conversation_unique_session.sql)；确认 `group_member.mute_reason` 尚不存在后执行 [MIG-02 字段迁移](../migrations/manual/MIG-02_member_mute_reason.sql)。现有 SQL 基线只影响新库，不会自动修改生产库。
2. 核对是否有客户端直接访问 VM 的 8081、8082、8084、8085、8086、8087、8089、8094 微服务端口。新 Compose 会把这些端口限制在 VM 本机；外部客户端需走 Nginx。旧 WAR 的 8080 暂保留对外访问，待确认现有客户端迁移到 Nginx 后再另行收口。
3. 在目标 VM 构建和启动新镜像后，执行目标 Nginx 容器 `nginx -t`、入口 HTTP 检查、旧 WAR 页面登录与项目/奖项/新闻/群组实际读写回归，并确认 13 个回退域及 2 个 503 域的行为。
   内容服务还需确认 `content-storage-init` 成功退出，并以 UID 1001 实际写入新闻目录；Nginx 能读取生成的文件。
4. 若目标是让微服务实际承接生产业务，还需逐域对照旧 WAR 的 `action`/页面/重定向与新 REST/JSON 契约，补适配或更新客户端，再按项目、奖项、新闻、群组、AI 分别切流和验证。当前路由不会自动切流。

**客户端契约核对：** 当前 JSP 页面主要调用旧 WAR 的 `/project?action=...`、`/award?action=...`、`/news?action=...`、`/group?action=...`，不是新的 `/api/...` REST 控制器。两套 API 的已确认差异如下；这里只记录缺口，不把新服务未覆盖的入口切入生产。

| 域 | 旧 WAR API / 页面 | 当前微服务 API 差异 |
|---|---|---|
| 项目 | `/api/projects/created-by-me`、图片、文件、标签、管理员转让等操作；页面走 `/project?action=...` | `ProjectController` 未提供全部同名路径；审批 HTTP 方法也不同。 |
| 奖项 | `/api/awards/types`、`categories`、`levels`、`competition-levels`、图片上传；页面走 `/award?action=...` | `AwardController` 尚无这些字典和上传入口，审批使用 `PUT` 而非旧 API 的 `POST`。 |
| 新闻 | `/api/news/types` 与 `POST` 方法覆盖；页面走 `/news?action=...` | `NewsController` 使用 `/type/{type}`、`PUT` 和 `DELETE`。 |
| 群组 | `/api/groups/my`、`created-by-me`、`/{id}/unmute`；页面走 `/group?action=...` | `GroupController` 使用按用户 ID 查询的路径及 `DELETE /{id}/mute`，成员级禁言另有新路径。 |
| AI 与认证 | AI 聊天页面使用 `/ai?action=...`；旧 WAR API 依赖登录会话 | `AiController` 使用 `/api/ai/*` 和 JWT，不能直接复用旧页面会话。 |

生产逐域切流前须补齐对应客户端/服务端契约并做真实读写回归，不能仅修改 Nginx 上游地址。本次用户选择暂不授权 SSH，后续只在本地继续修复和验证。
