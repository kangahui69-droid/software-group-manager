# DB-03 数据库运行账号切换

## 账号边界

Compose 中的旧 WAR、八个微服务和 Nacos 分别使用 `sg_app_svc`、`sg_file_svc`、`sg_user_svc`、`sg_activity_svc`、`sg_project_award_svc`、`sg_hr_svc`、`sg_monitor_svc`、`sg_content_svc`、`sg_ai_svc`、`sg_nacos_svc`。业务服务只获实际访问表的 DML 权限；旧 WAR 跨模块访问，因此只对其使用的业务表授予 DML。Nacos 账号只获 `nacos_config` 的 DML。任何运行账号都没有建表、授权、`mysql.*` 或 `flyway_schema_history` 权限。

MySQL root 仍用于数据库本身、Flyway 迁移和一次性的 `db-users-init` 管理任务；这两个管理任务结束后不作为业务服务运行。历史文件 `migrations/20261114_db_user_grants.sql` 已停用，不能用于新部署。新的授权文件为 `migrations/20261117_db03_runtime_grants.sql`，不含密码。

## 生产首次切换顺序

1. 先完成 DB-02 的备份、生产结构核对和显式 Flyway baseline；不要把未核对的生产库直接交给新 Compose。Nacos 的 `nacos_config` 仍按原手册独立建库。
2. 在 VM 的私有 `.env` 中，为 `.env.example` 所列 10 个 `*_DB_PASSWORD` 分别填入**不同的** 32–128 位随机字母、数字、下划线或连字符；例如用安全随机数工具生成 64 位十六进制值。不要把密码写进 Git、SQL、命令行参数或本手册。保持 `.env` 权限为 `600`。
3. 在 `/opt/software-group` 执行以下命令，检查每一步的退出码；任一步失败就停止发布并排查：

   ```bash
   bash scripts/check-deployment-secrets.sh
   docker compose run --rm --no-deps db-migrate
   docker compose run --rm --no-deps db-users-init
   ```

4. 用 MySQL 管理连接执行 `SHOW GRANTS FOR 'sg_app_svc'@'%';`、`SHOW GRANTS FOR 'sg_file_svc'@'%';`、`SHOW GRANTS FOR 'sg_nacos_svc'@'%';` 等，只查看授权，不在终端打印密码。确认账号可访问自己的表，不能访问其他服务库或 Flyway 历史表。
5. 再部署/重建旧 WAR、八个微服务和 Nacos，检查容器健康、登录、项目、内容、HR、AI、日志读写。旧 root 连接的业务容器在切换验证前保持运行；不要删除数据卷或停止整台 VM。确认新账号稳定后，另行核对并清理旧的 `*_svc` 账号及历史过宽授权。

新环境的 Compose 启动顺序为 MySQL → Flyway → `db-users-init` → Nacos/业务服务。`db-users-init` 对密码格式和重复值先做完整检查，再发送 SQL；同一密码再次执行可重复应用。**每次发布前仍应显式执行上述两个一次性任务**，不能依赖旧的已退出容器作为新迁移或授权已经执行的证明。

## 边界和待处理项

- `MYSQL_DATABASE` 目前必须为 `software_group`；授权脚本会拒绝其他库名。Nacos 使用独立的 `nacos_config`。
- 当前 `hr-service` 的简历 DAO 中有 5 个单数表名（`resume`、`resume_award`、`resume_education`、`resume_project`、`resume_skill`），而 V1 结构只有对应复数表。DB-03 只给实际存在的复数表授权；该业务 SQL 错误需单独确认和修复，授予 root 也不能使不存在的表正常工作。
- 本次尚未连接生产 VM，也没有在线创建账号或重建容器。数据库端口暴露范围由 OPS-01 单独处理。
