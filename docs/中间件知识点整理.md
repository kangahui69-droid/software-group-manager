# 我第一次用中间件：用一个真实项目，把「中间件」讲明白

> **摘要**："中间件"这三个字特别劝退——听起来像"夹在中间的什么东西"，又抽象又玄。直到我做那套高校管理系统，把 MySQL、Redis、RabbitMQ、MinIO、Nacos、Sentinel 一个个接进项目，才想明白它其实特别朴素：**中间件就是软件世界的"市政基础设施"**——那些通用、跟业务无关、又特别难写对的底层能力，交给专业服务去做。这篇文章记的是我理清这件事的过程，用我自己的项目当标本。

---

## 一、引子：没有中间件的时候，什么都要自己造

"中间件"这个名字劝退，是我真正想明白它，靠在脑子里做的一个对比：**如果这些中间件都不存在，我得自己写什么？**

| 没有中间件 | 我得自己干的事 |
|---|---|
| 没有 MySQL | 自己设计一套文件存储格式、自己实现查询、自己处理并发写、自己保证不丢数据 |
| 没有 Redis | 自己写一套内存缓存 + 过期清理 + 淘汰策略 |
| 没有 RabbitMQ | 自己写一套"任务排队"的机制，还要处理崩溃后任务不丢 |
| 没有 Nacos | 8 个服务的地址全写死在配置里，谁换 IP 就全崩 |
| 没有 MinIO | 用户上传的文件自己存磁盘、自己生成下载链接、自己处理大文件 |

**每一样都是"通用的、跟业务无关的、又特别难写对"的东西。** 全自己造，造一年也造不完，造出来还一堆 bug。

于是软件世界的分工出现了：**有人专门把这些"通用的基础能力"做成独立的产品，你需要时连上去用就行。** 这就是中间件。

---

## 二、中间件到底是什么

> **中间件 = 一个已经造好的、能独立运行的"通用基础服务"，你的业务代码通过网络连上它、使用它的能力，不用自己实现。**

打个比方：开餐厅，你**不用自己发电、自己挖井、自己修路**——交给市政就行。你要做的只是"接上电、接上水、接上网络"，然后专心做菜。

**中间件就是软件世界的"市政"**：

```
   市政基础设施              软件中间件
   ─────────────           ────────────
   发电厂          ←→       MySQL（存数据）
   自来水厂        ←→       Redis（做缓存）
   物流快递        ←→       RabbitMQ（传消息）
   114 查号台      ←→       Nacos（找服务）
   仓库/物流园     ←→       MinIO（存文件）
```

**两个关键认知**：

1. **中间件是一个独立的进程/服务，不是你的代码库。** 你的代码是"客户"，它是"供应商"，中间隔着一根网线（`localhost:3306` 这种）。
2. **它跟你的业务无关。** MySQL 不知道你存的是用户还是订单；Redis 不知道你缓存的是活动还是奖项。它只提供**通用能力**，怎么用是你的事。

---

## 三、一个必须分清的区分：中间件 vs 库

新手最容易把这两个混在一起。看我项目里的两个东西：

| | 一个库（jar 包） | 一个中间件 |
|---|---|---|
| 例子 | Gson、Jsoup | MySQL、Redis、RabbitMQ |
| 形态 | **一段代码**，打包进你的 WAR/JAR | **一个独立进程**，跑在容器里 |
| 怎么用 | `import` 然后直接调方法 | 通过网络**连接**它、发命令 |
| 生命周期 | 跟着你的程序一起启动/停止 | **独立存活**，你的程序挂了它还活着 |
| 我项目里的体现 | `pom.xml` 里一个 `<dependency>` | `docker-compose.yml` 里一个 `service` |

**一句话记法**：**库是"装进你身体里的器官"，中间件是"住在你隔壁的邻居"——你得敲门（连网络）才能用。**

> 这也是为什么这一篇一定要紧接在 Docker 之后：**我项目里这 6 个中间件，全都是 Docker 容器**。`docker-compose.yml` 里 `mysql:`、`redis:`、`rabbitmq:`、`nacos:`、`sentinel:`、`minio:` 这 6 个 service，就是它们。

---

## 四、我项目用了哪 6 个中间件（总览）

| 中间件 | 类型 | 一句话作用 | 跑在哪个容器 |
|---|---|---|---|
| **MySQL** | 关系型数据库 | 把数据持久化存下来（45 张表） | `mysql:8` |
| **Redis** | 内存 KV 存储 | 做业务缓存；旧 WAR 的 Session 目前由单实例 Tomcat 管理 | `redis:7-alpine` |
| **RabbitMQ** | 消息队列 | 把慢任务丢进队列，异步处理 | `rabbitmq:3-management-alpine` |
| **Nacos** | 注册中心 + 配置中心 | 微服务的"通讯录"（+ 集中配置） | `nacos-server:v2.2.3` |
| **Sentinel** | 流量防护 | 熔断、限流，防止雪崩 | `sentinel-dashboard` |
| **MinIO** | 对象存储 | 存用户上传的文件（头像、附件） | `minio/minio` |

下面**重点讲 MySQL / Redis / RabbitMQ / MinIO** 这 4 个业务用得最多的，Nacos / Sentinel 只做补充（它们更偏"微服务时代"的范畴）。

## 五、逐个讲：它们分别解决什么问题

### ① MySQL —— 数据要"落地"，不能只在内存里

**要解决的问题**：程序一重启，内存里的数据就没了。用户注册的账号、发的活动，必须**永久存下来**。

如果不用数据库，你得自己写文件、自己处理"两个人同时改同一条记录"、自己实现"查年龄大于 18 的所有用户"……**关系型数据库把这些都替你做了**（SQL 查询 + 事务 + 并发控制 + 崩溃恢复）。

**我项目怎么用**：通过 `DBUtil`（HikariCP 连接池）拿连接，DAO 层写 SQL：

```java
public User findById(Integer id) {
    String sql = "SELECT * FROM user WHERE id = ?";
    conn = DBUtil.getConnection();      // 连 MySQL
    pstmt = conn.prepareStatement(sql);
    ...
}
```

**它是这 6 个里最重要、最不可替代的一个**——其他中间件都可以"暂时没有"（降级），但数据库没了系统就没了。

### ② Redis —— 让"读"变快，以及存"会过期的东西"

**要解决的问题有两个**：

**(a) 数据库太忙。** 有些数据被反复读（比如字典表、奖项筛选条件），每次都查 MySQL 太浪费。放进 Redis（内存），读起来快几百倍。

我项目里 `AwardService` 就是干这个的：

```java
String cached = RedisUtil.get(cacheKey);                 // 先问 Redis
...
RedisUtil.set(cacheKey, json, CacheConsts.TTL_DICTIONARY); // 没有就查库，然后写进 Redis
```

**这叫"缓存"**——像一个放在 MySQL 门口的"常用抽屉"，不用每次跑仓库。

**(b) Session 没法共享。** 当前旧 WAR 的 Session 存在单实例 Tomcat 中；用户在 A 实例登录后，请求被转到 B 实例不会保持登录。旧版 `SessionRedisFilter` / `RedisSessionUtil` 只写入 Redis，没有真正恢复 Session，已在 OPS-05 中移除。若将来需要多实例，必须先接入并验证成熟的容器级会话管理方案。

**为什么用 Redis 而不是普通 Map？** Redis 支持 TTL，且独立于 Tomcat 进程；Redis 重启后能否保留数据取决于持久化配置。当前项目只用它处理业务缓存，不能据此认为旧 WAR 的 Session 已共享。

### ③ RabbitMQ —— "慢活儿"别让用户干等（这是最值得慢慢讲的）

**要解决的问题**：AI 对话要调外部大模型，**可能要好几秒**。如果同步处理：

```
用户 → 后端 → 调大模型（卡 5 秒）→ 返回
         ↑ 这 5 秒里，用户的浏览器在转圈
         ↑ 服务器的一个线程被死死占住，100 个用户 = 100 个线程全阻塞
```

**解法：把"要花时间的活儿"从主流程里拆出去，异步做。**

我项目的 `AIMessageConsumer` 就是标准范例。

**第一步（生产者）**：用户发消息，后端**不直接处理**，而是把消息扔进队列，立刻返回一个"受理号"，让前端去轮询：

```java
public static String sendToQueue(String message, Integer userId, ...) {
    String messageId = UUID.randomUUID().toString();               // 生成"受理号"
    statusDAO.insert(new AIMessageStatus(messageId, ...));         // 状态：待处理
    RabbitMQUtil.sendMessage("ai.exchange", "ai.message", json);   // 扔进队列，立刻返回
    return messageId;                                              // 用户拿到受理号
}
```

**第二步（消费者）**：后台一个线程，从队列里**慢慢取**，调 AI、拿结果、更新状态：

```java
DeliverCallback deliverCallback = (consumerTag, delivery) -> {
    Map message = gson.fromJson(body, Map.class);
    statusDAO.updateStatus(messageId, STATUS_PROCESSING, ...);              // 状态：处理中
    String aiResponse = aiService.getAIResponse(...);                       // 花 5 秒也行
    statusDAO.updateStatus(messageId, STATUS_COMPLETED, aiResponse, ...);   // 状态：完成
    channel.basicAck(...);                                                  // 确认："这条我处理完了"
};
```

**前端**则拿着受理号不停问"好了没"（轮询 `getMessageStatus`）。

**看明白了吗？** 用户**瞬间**就拿到了响应（"已受理"），后台慢慢算，算完前端再取。**这就是消息队列的核心价值：解耦 + 异步 + 削峰。**

**几个必懂的核心概念**（都在我项目代码里）：

| 概念 | 在我项目里 | 作用 |
|---|---|---|
| **生产者** | `sendToQueue`（用户发消息时） | 往队列里**放**消息 |
| **消费者** | `AIMessageConsumer.consumeLoop` | 从队列里**取**消息处理 |
| **交换机 Exchange** | `ai.exchange`（direct 类型） | 决定消息该往哪个队列走 |
| **队列 Queue** | `ai.message.queue` | 消息排队等待的地方 |
| **路由键 Routing Key** | `ai.message` | 交换机靠它把消息路由到对应队列 |
| **ACK 确认** | `channel.basicAck(...)` | 消费者说"处理完了"，消息才删除 |
| **NACK** | `channel.basicNack(...)` | 处理失败，拒绝（可决定是否重新入队） |

> **ACK 机制是消息队列的灵魂**：如果消费者处理到一半崩了、没发 ACK，RabbitMQ 会把消息**重新投递**给别的消费者——所以消息不会因为一个进程崩溃而丢。这是"自己用内存队列"做不到的。

### ④ MinIO —— 文件别塞数据库，也别塞本地磁盘

**要解决的问题**：用户上传的头像、附件怎么存？

- 塞进 MySQL？**不行**——大二进制文件会让数据库暴胀、变慢。
- 塞本地磁盘？**不够好**——多实例部署时，A 机器存的文件 B 机器读不到；也没有备份、扩容、权限控制。

**解法：对象存储（Object Storage）**。MinIO 就是一个"私有的、你能自己部署的 S3"。它专门存文件，给你三个好东西：**统一访问入口**、**预签名 URL**（临时授权下载链接）、**无限扩容**。

**我项目怎么用**（`file-service`）：`MinioConfig` 启动时自动建桶，`FileService` 里上传 / 下载 / 删除：

```java
// 上传
minioClient.putObject(PutObjectArgs.builder().bucket(bucket)...stream(...).build());

// 生成一个"临时下载链接"（关键！）
String url = minioClient.getPresignedObjectUrl(...);

// 删除
minioClient.removeObject(RemoveObjectArgs.builder().bucket(bucket).object(objectName).build());
```

**`getPresignedObjectUrl` 这个设计特别妙**：后端不把文件流转发给浏览器，而是**生成一个带签名的、限时有效的 URL**，浏览器直接去 MinIO 拿。**后端的流量负担一下就没了。**

### ⑤ Nacos / ⑥ Sentinel —— 补充一句

- **Nacos**：它是**双重中间件**——既是**注册中心**（服务的通讯录），也是**配置中心**（集中管理 8 个服务的配置）。属于"微服务时代的中间件"。
- **Sentinel**：**流量防护中间件**——当一个服务调用持续失败，快速熔断，防止故障像多米诺骨牌一样传染。

## 六、"中间件思维"：什么时候该引入一个中间件？

这是比"知道有哪些中间件"更重要的问题。我总结的判断表：

| 当你遇到这个问题…… | 该考虑的中间件类型 | 我项目里的例子 |
|---|---|---|
| 数据要永久保存 / 要复杂查询 | 关系型数据库 | MySQL |
| 某些数据被反复读、怕慢 | 缓存 | Redis |
| 一个操作**很慢**、不想让用户等 | 消息队列 | RabbitMQ |
| 多个实例要**共享状态**（如 Session） | 缓存 / 分布式存储 | Redis |
| 有**大文件**要存 | 对象存储 | MinIO |
| 多个服务要**互相找到** | 注册中心 | Nacos |
| 怕一个服务故障**拖垮全系统** | 熔断 / 限流 | Sentinel |

**一句心法**：**"凡是通用的、跟业务无关的、又难写对的底层能力——别自己造，找中间件。"**

反过来说，也有**不该用**的时候：

- 数据量极小、单机、且不介意丢 —— 用个文件或内存 Map 就够了，上 Redis / MySQL 是过度设计。
- 一个 1 秒能算完的活儿 —— 别为了"看起来高级"套个消息队列，那只是增加复杂度。

**判断标准永远是"痛点是否真实存在"，而不是"这个中间件听起来很牛"。**

## 七、中间件的"使用套路"：其实就三步

我项目里每一个中间件的封装，都遵循**同一个套路**——看懂这个套路，你就"会用"了：

| 步骤 | 干什么 | 我项目里的对应 |
|---|---|---|
| ① **配置连接** | 地址/端口/账号从配置读，不要写死 | `Config.getProperty("redis.host")` |
| ② **封装工具类** | 把连接、执行、关闭包成一个静态方法 | `RedisUtil` / `RabbitMQUtil` / `DBUtil` |
| ③ **业务调用** | Service 层直接调工具类，不管底层细节 | `AwardService` 调 `RedisUtil.get(...)` |

看 `RedisUtil` 就是标准的第②步——**把"拿连接 → 执行 → 关连接"封装好**：

```java
public static String get(String key) {
    try (Jedis jedis = getJedis()) {     // 从连接池拿
        return jedis.get(key);           // 执行
    }                                    // try-with-resources 自动关
}
```

**业务代码只写 `RedisUtil.get("award:dict")`**，完全不用知道 Redis 的协议、连接、密码。**这就是"会用中间件"的样子——调用方只关心"要什么能力"，不关心"怎么连"。**

而连接信息，全都来自配置 / 环境变量（回到 Docker 篇：同一份镜像，换套环境变量就连不同的中间件）：

```java
connectionFactory.setHost(Config.getProperty("rabbitmq.host", "localhost"));
connectionFactory.setPort(Config.getIntProperty("rabbitmq.port", 5672));
```

## 八、我脑子里的那张中间件地图

```
   你的业务代码（Service / DAO）
        │  通过"工具类"连中间件（RedisUtil / RabbitMQUtil / DBUtil）
        ▼
   ┌──────────────────────────────────────────────────┐
   │                    中间件（都是 Docker 容器）        │
   │                                                    │
   │  ┌────────┐ ┌───────┐ ┌──────────┐               │
   │  │ MySQL  │ │ Redis │ │ RabbitMQ │               │
   │  │存数据   │ │业务缓存│ │异步消息 │             │
   │  └────────┘ └───────┘ └──────────┘               │
   │  ┌────────┐ ┌──────────┐ ┌────────┐              │
   │  │ MinIO  │ │  Nacos   │ │Sentinel│              │
   │  │存文件   │ │注册/配置 │ │熔断    │              │
   │  └────────┘ └──────────┘ └────────┘              │
   └──────────────────────────────────────────────────┘
        ▲ docker-compose 一条命令全拉起来

   核心三问：它解决什么"通用且难写"的问题？
            我的业务通过什么"客户端/工具类"连它？
            连不上/挂了，我的系统能不能降级？
```

**我现在的理解浓缩成三句话**：

1. **中间件 = 独立进程的"通用基础服务"**，跟"库"的本质区别是——**库在你身体里，中间件在你隔壁，得连网络**。
2. **判断要不要用它，看"痛点是否真实"**：要落地找数据库、要加速找缓存、要异步找消息队列、要存文件找对象存储、要互相找找注册中心。
3. **"会用" = 会走那三步套路**：配置连接 → 封装工具类 → 业务调用；**调用方只关心能力，不关心实现**。

拿到一个新需求，我现在会问三个问题：

- 这里面有没有**"通用且难写"的底层能力**？（有 → 找现成中间件，别自己造）
- 我该用**哪个客户端/工具类**去连它？（项目里通常已经封装好了）
- **它挂了，我的系统会怎样**？（想清楚降级方案，尤其是数据库之外的每个中间件）

## 九、收尾：五级台阶

我这几篇摸索下来，正好是**同一个系统演进的一条完整链**：

```
① Docker      —— 怎么把服务（含中间件）装进盒子、编排起来跑   （运行环境）
② 服务分层    —— 盒子里的代码怎么按职责分成三层              （代码结构）
③ API 化      —— 分层的 Service 怎么开标准数据出口           （对外契约）
④ 微服务      —— 把干净的 API 边界切成独立进程               （部署形态）
⑤ 中间件      —— 那些"通用又难写"的能力，交给专业服务        （基础能力）
```

**一条线串到底**：Docker 让盒子**跑得起来**，中间件让盒子**有了水电煤**，服务分层让盒子里**理得顺**，API 化让盒子**说得清**，微服务让盒子**各立门户又互相协作**。**它们不是竞争关系，而是一层叠一层的脚手架。**

---

*如果你也是第一次用中间件：别一上来就背"有哪些中间件、各自什么特点"。先问自己一句"我现在这件事，有没有一个通用的、我根本写不好的底层能力"，然后去找对应的中间件——找不到合适的，就先不上。中间件这件事，考验的是你对自己痛点的判断，而不是对产品的熟悉。*
