# 我第一次做服务分层：用一个真实项目，把 Servlet / Service / DAO 三层讲明白

> **摘要**：做重构之前，我以为"服务分层"是个很虚的架构词，无非就是把代码拆成几个文件。真正动手把一个真实项目——高校软件小组管理系统——从"一个方法里塞满 SQL、业务判断和 HTTP 响应"改成三层之后，我才明白：**分层的本质不是"多写几个类"，而是让"接请求的、定规则的、存数据的"各回各家**。这篇文章记的是我理清这件事的过程，用我自己的项目当标本，一层一层拆给你看。

---

## 一、引子：不分层的时候，代码长什么样

我项目里有段时间，一个 Servlet 方法大概是这样（示意，别笑）：

```java
// ❌ 重构前的"上帝类"：一个方法干了三件事
protected void doPost(HttpServletRequest req, HttpServletResponse resp) {
    String username = req.getParameter("username");      // ① 接请求、解析参数
    if (username.length() > 32) { /* 太长 */ }            // ② 业务规则
    Connection conn = DBUtil.getConnection();             // ③ 直接跟数据库说话
    PreparedStatement ps = conn.prepareStatement("INSERT INTO user ...");
    ps.executeUpdate();
    resp.getWriter().write("{\"code\":0}");               // 回到 ① 手拼 JSON
}
```

**一个方法，既懂 HTTP、又懂业务规则、又懂 SQL。**

一开始能跑，但很快就开始疼：

- **改一处，怕动全身**：菜单上想改个提示语，结果手滑动了 SQL，线上就炸。
- **测不了**：想单测"用户名重复怎么办"，得先起一个 Tomcat、连上数据库——因为这段逻辑和 HTTP、数据库焊死在一起。
- **复用不了**：同样的"创建用户"逻辑，网页要用，将来小程序也要用，难道复制一份 SQL 过去？

这三点疼到一定程度，我就知道该重构了。方向很明确：**把这件事按职责切开。** 这就是服务分层。

---

## 二、服务分层到底是什么？

我现在是这么理解的：

> **服务分层 = 把"处理一个功能请求"这件事，按职责切成几段，每段只管自己那一段，段与段之间用清晰的方法调用连接。**

我那套系统切成了三段（外加几个配角）：

```
浏览器请求
   │
   ▼
┌──────────────────────────────────────────────┐
│ ① API 层（Servlet）      —— "点菜员"           │
│    只做：接请求、解析参数、调 Service、返回JSON │
│    不碰：SQL、业务规则                          │
├──────────────────────────────────────────────┤
│ ② Service 层             —— "厨师"             │
│    只做：业务规则、校验、事务、拼装数据          │
│    不碰：HttpServletRequest、写死的SQL          │
├──────────────────────────────────────────────┤
│ ③ DAO 层                 —— "冷库管理员"        │
│    只做：跟数据库说话（增删改查 SQL）           │
│    不碰：业务判断                              │
└──────────────────────────────────────────────┘
   │
   ▼
 MySQL
```

打个餐馆的比方：**点菜员**记下客人要什么（接请求），**厨师**决定这道菜怎么做、放多少盐（业务规则），**冷库管理员**只管去冷库拿食材（读写数据）。三个人各干各的，谁都不越界。

对应到我的项目目录，三层是这样落地的：

| 层 | 目录 | 职责一句话 | 规模 |
|---|---|---|---|
| ① 表现层 / API 层 | `src/main/java/servlet/api/` | 接请求、回 JSON | 14 个 `*ApiServlet` |
| ② 业务层 | `src/main/java/service/` | 业务规则 + 事务 | 15 个 `*Service` |
| ③ 数据访问层 | `src/main/java/dao/` | 只管 SQL | 31 个 `*DAO` |

还有几个**配角**（不属于三层，但每层都要用）：

| 配角 | 目录 | 作用 |
|---|---|---|
| `model/` | 实体 | 数据库表的 Java 影子（`User`、`Award`…） |
| `dto/` | 传输对象 | 层与层之间传的"打包数据" |
| `util/` | 工具 | `Result`（统一响应）、`DBUtil`（连接池）、`TransactionTemplate`（事务） |

---

## 三、铁律：每一层"只做什么、绝不做什么"

这是分层的灵魂。我项目的重构计划里有一句话，是我整个重构的行动纲领：

> **先有 Service 层，后有 API 层。Service 是业务逻辑的核心，API Servlet 应该是"薄"的。**

具体到"该不该写"这张表，我贴在了工位上：

| | API 层（Servlet） | Service 层 | DAO 层 |
|---|---|---|---|
| 读 `req.getParameter()` | ✅ 只它读 | ❌ 绝不 | ❌ |
| 写业务判断（"用户名重复了"） | ❌ | ✅ 只它写 | ❌ |
| 写 SQL / 开事务 | ❌ | ❌ | ✅ 只它写 |
| 决定 HTTP 状态码 | ✅ | ❌（只返回 `Result`） | ❌ |

**我记住的记法**：谁离"外面的世界"近，谁就管外面的世界。

- Servlet 离浏览器近 → 管 HTTP；
- Service 离规则近 → 管业务；
- DAO 离数据库近 → 管 SQL。

## 四、用真实代码走一遍：以"创建成员"为例

光说规则太虚，我拿项目里最普通的一个接口走一遍：`POST /api/members`，请求体是 `{"username":"zhao","password":"123456","role":"MEMBER"}`。

### 第 ① 层：API Servlet 接住请求

```java
// MemberApiServlet.java
private void handleCreate(HttpServletRequest req, HttpServletResponse resp, User user) throws IOException {
    Map<String, Object> dto = (Map<String, Object>) parseJsonRequest(req);  // 解析 JSON
    if (dto == null) {
        sendBadRequest(resp, "请求体不能为空");                              // 只管"参数在不在"
        return;
    }
    writeJson(resp, memberService.createMember(dto));                        // 甩给 Service，结果转 JSON
}
```

看清楚它做了什么：**解析 JSON → 调 `memberService.createMember` → 把返回值写回 JSON。仅此而已。**

它**不问**用户名是否重复、**不碰**数据库——那是下一层的事。这就是"薄 Servlet"。

再看它的头部，是整条调用链的起点：

```java
private transient MemberService memberService;

@Override
public void init() throws ServletException {
    super.init();
    this.memberService = new MemberService();   // Servlet 持有 Service 的引用
}
```

### 第 ② 层：Service 做业务

```java
// MemberService.java
public Result createMember(Map<String, Object> dto) {
    Result validation = validateCreateMemberInput(dto);        // ① 业务校验
    if (validation != null) return validation;

    String username = extractString(dto, "username");
    // ...
    try {
        if (userDAO.findByUsername(username) != null) {         // ② 业务规则：查重
            return Result.error(400, "用户名已存在");
        }
        User user = buildUserForCreate(username, password, role, dto, email, phone);
        boolean inserted = userDAO.insert(user);                // ③ 交给 DAO 落库
        if (!inserted) {
            return Result.error(500, "创建成员失败");
        }
        return Result.ok(user);                                 // ④ 返回统一结果
    } catch (Exception e) {
        return Result.error(500, "创建成员失败: " + e.getMessage());
    }
}
```

**这一层是"大脑"**：

- `validateCreateMemberInput` —— 业务校验（用户名长度、密码规则）；
- `findByUsername` 查重 —— **业务规则**（"用户名只能唯一"是业务定的，不是数据库定的）；
- 调 `userDAO.insert` —— 落库这一步**委托**给下一层；
- 返回 `Result` —— **不自己拼 JSON、不设 HTTP 状态码**，只说"成功/失败 + 错误码"。

而且一个 Service **可以组合多个 DAO**：

```java
private final UserDAO userDAO;
private final MemberProfileDAO memberProfileDAO;
private final FileStorageDAO fileStorageDAO;
// ...
```

这正是 Service 存在的意义之一——**DAO 各查各的表，Service 把结果拼装成一个完整的业务对象**。比如"成员详情"要同时查 `user` 表 + `member_profile` 表，就是 Service 在中间组装。

### 第 ③ 层：DAO 跟数据库说话

```java
// UserDAO.java
public User findById(Integer id) {
    String sql = "SELECT * FROM user WHERE id = ?";   // ← 这里才出现 SQL
    Connection conn = null;
    PreparedStatement pstmt = null;
    ResultSet rs = null;
    try {
        conn = DBUtil.getConnection();                 // 从连接池拿连接
        pstmt = conn.prepareStatement(sql);
        pstmt.setInt(1, id);
        rs = pstmt.executeQuery();
        if (rs.next()) {
            return mapResultSetToUser(rs);             // 结果集 → Java 对象
        }
    } catch (SQLException e) {
        e.printStackTrace();
    } finally {
        closeResources(conn, pstmt, rs);               // 关资源
    }
    return null;
}
```

**DAO 只做一件事：把"参数"翻译成"SQL"，把"结果集"翻译回"对象"。** 它不做任何业务判断——`findById` 不知道调用它的方法是谁、要干嘛，它只管查。

### 串起来看这一条链

```
POST /api/members
   │
   ▼  MemberApiServlet.handleCreate   ← ① 解析 JSON，"参数对不对"
   │      memberService.createMember(dto)
   ▼  MemberService.createMember      ← ② 业务校验 + 查重 + 决定要落库
   │      userDAO.insert(user)
   ▼  UserDAO.insert                  ← ③ 生成 INSERT SQL，执行
   │
   ▼  MySQL
   ▲
   │  Result.ok(user)                 ← ② 包成统一结果
   │      writeJson(resp, result)
   ▲  BaseApiServlet.writeJson        ← ① 序列化成 JSON，设 HTTP 200
{ "code":0, "message":"ok", "data":{...} }
```

**每一层只跟相邻的一层说话**——Servlet 只调 Service，Service 只调 DAO，谁都不"越级"。

## 五、三个必须搞懂的关键机制

### 1. 为什么 Service 返回 `Result` 而不是直接写 JSON？

`Result` 是一个**只有数据、不懂 HTTP** 的普通对象：

```java
public static Result ok(Object data)                  { return new Result(0, "ok", data); }
public static Result error(int code, String message)  { return new Result(code, message, null); }
public boolean isSuccess()                            { return code == 0; }
```

好处有两点，我踩过才知道有多值：

- **Service 不依赖 Servlet API**，所以能被单元测试直接调用——不用起 Tomcat；
- **"业务码"和"HTTP 码"分开**：Service 说"这是 400 错误"，Servlet 里的 `resolveHttpStatus()` 才决定把它翻成 HTTP 400。同一段 Service 逻辑，将来给网页用（返回 JSON）、给别的调用方用（转发页面）都行。

### 2. 事务属于哪一层？——**Service 层**

跨表写操作（比如"创建成员"要同时写 `user` 和 `member_profile`）必须"要么全成功、要么全回滚"。这个动作由 `TransactionTemplate` 提供，**调用点在 Service**：

```java
return TransactionTemplate.executeWithConnection(conn -> {
    int id = xxxDAO.insert(entity, conn);   // 同一个 conn，两个操作绑在一个事务里
    xxxDAO.update(other, conn);
    return Result.ok(/* ... */);            // 抛出 RuntimeException → 自动回滚
});
```

**为什么事务在 Service 而不在 DAO？** 因为"这两步要一起成功"是**业务决定**的。DAO 只负责"插一行"，它不知道这件事要跟别人绑在一起。

> **多个 DAO 操作的组合 + 原子性 = 业务逻辑 = Service 的活。**

### 3. 为什么 Service 有两个构造函数？

```java
public MemberService() {                      // 运行时用：自己 new 真实 DAO
    this.userDAO = new UserDAO();
    // ...
}

public MemberService(UserDAO userDAO, /* ... */) {  // 测试时用：传入 mock 的 DAO
    this.userDAO = userDAO;
    // ...
}
```

这叫**构造器注入**。它不是"多余"，而是分层带来的**测试红利**：分层后 DAO 可以被替换成假的（mock），于是你能**不连数据库**就测业务逻辑。我的项目没有引入 Spring，靠的就是这个构造函数重载，把"可测试性"拿到了手。

## 六、动手：以后加新功能，标准动作是什么

想清楚分层之后，我给自己定了一套动作，加任何新功能都照这个顺序走：

| 步骤 | 动哪一层 | 干什么 | 能不能跳过 |
|---|---|---|---|
| 1 | **Service** | 写业务方法（先写测试，TDD） | ❌ 核心 |
| 2 | **DAO** | 缺 SQL 就补一个查询/写入方法 | 仅在需要新 SQL 时 |
| 3 | **API Servlet** | 加一个 handler：解析参数 → 调 Service → `writeJson` | ❌ |
| 4 | **web.xml** | 注册路由 | 记得别漏 |
| 5 | **测试** | Service 测试 + API 测试 | ❌ |

**最关键的原则：先 Service，后 API。**

因为 Service 是"可复用的业务核心"，API Servlet 只是它的"一个出口"——将来还会再挂别的出口（JSP、微服务、定时任务）。

而很多人第一次做分层会犯的错，是在 Servlet 里直接写 SQL：

```java
// ❌ 在 Servlet 里直接写 SQL —— 分层就白做了
protected void doPost(HttpServletRequest req, HttpServletResponse resp) {
    Connection conn = DBUtil.getConnection();
    PreparedStatement ps = conn.prepareStatement("INSERT INTO ...");  // 越级了！
}
```

一旦这么写，"改一处怕动全身"的病就复发了。

## 七、我自己的项目迁移到什么程度了

| 层 | 完成度 |
|---|---|
| DAO（31 个） | ✅ 早已存在 |
| Service（15 个） | ✅ 全部完成 |
| API Servlet（14 个） | ✅ 全部完成 |
| 测试用例 | 1500+ |

也就是说，**这套系统现在已经是"三层俱全"的样本了**。我平时随手读的 `MemberService` / `MemberApiServlet` / `UserDAO`，就是最终形态。

有个后话值得一提：后来把系统拆成 8 个微服务时，我发现**那是同一个思想再走一步**——每个微服务内部照样是三层：

```
Controller (≈ 我这里的 Servlet)
    │
Service
    │
Mapper / Repository (≈ 我这里的 DAO)
```

只不过从一个进程里的三个包，变成了独立部署的三个进程。**分层是"纵向切职责"，微服务是"横向切业务"，两个维度正交，可以叠加。** 想通这一层，我对整个项目的架构就不慌了。

## 八、我脑子里的那张分层地图

如果只留一样东西，我会留下这张图：

```
        接请求 ──▶ Servlet（薄）   解析参数 · 返回 JSON
                       │
                       ▼
        定规则 ──▶ Service（厚）   业务校验 · 事务 · 组合多个 DAO
                       │
                       ▼
        存数据 ──▶ DAO（纯）       只写 SQL · 结果集 ⇄ 对象
                       │
                       ▼
                     MySQL

   统一响应 ──▶ Result           {"code","message","data"}
   事务边界 ──▶ TransactionTemplate   在 Service 层包裹多 DAO 操作
```

**我现在的理解浓缩成三句话**：

1. **分层不是"多写几个类"，是让接请求的、定规则的、存数据的各回各家。**
2. **Servlet 要薄，Service 要厚，DAO 要纯**；每一层只跟相邻的一层说话，谁都不越级。
3. **Service 是一个可复用的业务核心，API 只是它的一个出口**——所以永远先写 Service，再写 API。

拿到任何一段代码，我现在会问自己三个问题：

- 这段代码**离谁近**？（HTTP / 业务 / 数据库）
- 它**该不该**知道隔壁层的事？（Servlet 不该知道 SQL，DAO 不该知道业务规则）
- 我要改的功能，**该落在哪一层**？（改路由→Servlet；改规则→Service；改表/查询→DAO）

---

*如果你也是第一次做服务分层：别急着背"三层""四层"的概念，先找一段自己写的、又臭又长的方法，试着把里面的 SQL 抽到 DAO、把业务判断抽到 Service，看看剩下那个 Servlet 是不是一下就"薄"了。分层这件事，讲一百遍不如亲手抽一次。*
