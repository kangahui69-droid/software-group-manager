# 微信小程序改造方案（成员端核心六项）

> 状态：已确认，待实施
> 日期：2026-10-28
> 范围：成员端六项高频功能，管理端继续保留 PC

## 一、背景与目标

现有系统是「JSP 单体 WAR + 8 个 Spring Boot 微服务」的混合架构，只有 PC 网页端。计划新增微信小程序，让成员在手机上完成高频操作。

已确认的产品决策：

- 形态：微信小程序
- 前端：Taro 3.x + React + TypeScript
- 登录：账号密码登录，复用现有 `user-service` 的 JWT
- 群聊：5–10 秒轮询，首期仅文本消息
- 新闻：后端返回 HTML，小程序用 `rich-text` 渲染
- AI：会话历史持久化到数据库
- 资质：暂无小程序 AppID，先用测试号开发；项目自用，不涉及支付

首期功能：**登录/个人中心、活动报名、考勤打卡、群聊消息、新闻/通知、AI 助手**。

首期不做：管理端移动化、微信登录/openid 绑定、WebSocket、支付、简历/项目/奖项、消息推送、群聊图片/文件、PC 端 JSP 迁移。

## 二、必须先修的三个事实

调研发现以下问题，不修则小程序无法可靠上线：

1. **content-service 的群聊/新闻 DAO 是桩实现**
   - `GroupMessageDAO` 查询恒返回空列表、`insert` 恒返回 1
   - `NewsDAO`、`GroupMemberDAO`、`UserGroupDAO`、`ActivityGroupDAO` 同样为桩
   - Nginx 已把 `/api/groups`、`/api/news` 指向该服务，因此这两个模块目前实际不可用

2. **鉴权形同虚设**
   - 仅 `activity`、`file`、`user` 三个服务有 JWT 过滤器
   - `activity-service/.../config/JwtAuthFilter.java` 把 `/api/activities|attendance|study` 全部放行
   - 过滤器只写 request attribute，不注入 Controller 依赖的 `X-User-Id` 请求头
   - `content/hr/monitor/project-award/ai` 无过滤器，直接信任可伪造的 `X-User-Id`
   - `common/.../util/JwtUtil.java` 密钥硬编码

3. **没有网关和统一入口**
   - Nginx 按前缀逐条分流（`nginx/nginx.conf`）
   - 移动端需要单一入口与统一 401 行为

## 三、目标架构

```
微信小程序 (Taro)
   │ HTTPS  (Authorization: Bearer <JWT>)
   ▼
Nginx (80/443)  ── /software-group/*, /localstorage/* ──► 单体 WAR（PC，Session）
   │
   └── /api/* ──► gateway-service:8088（Spring Cloud Gateway）
                     │ 统一校验 JWT、剥离伪造头、注入 X-User-Id/Username/Role
                     ├──► file 8081 | user 8082 | activity 8084 | project-award 8085
                     ├──► monitor 8086 | content 8087 | hr 8089 | ai 8094
                     └── 静态 URI 优先，稳定后切 Nacos lb://
```

设计要点：

- 网关是策略点，各服务仍需 JwtAuthFilter：容器端口在宿主机暴露，不能只靠网关；每个服务只信任自己从 token 解析出的身份。
- 小程序图片/头像统一走 `GET /api/files/{id}/view`，不依赖内网 MinIO 预签名地址。
- AI 首期用同步 `POST /api/ai/chat`，不做 SSE。

## 四、实施阶段

### M0 外部准备（1–2 人日，非代码阻塞）

- 注册个人主体小程序 AppID；开发期用测试号 + 微信开发者工具「不校验合法域名」
- 小程序备案、HTTPS 证书、request/uploadFile 合法域名配置；内网穿透域名通常不适合做合法域名，上线前需固定公网入口
- 建分支 `feature/miniapp`，保留当前 Nginx 配置作为回滚点

### M1 鉴权底座 + 网关（4–6 人日，阻塞首期）

**新增 `common-auth` 模块**（解决 Gateway WebFlux 与 `common` 的 `spring-boot-starter-web` 冲突）

- `common-auth/src/main/java/com/softwaregroup/common/util/JwtUtil.java`：从 `common` 迁出，保持包名；密钥改为读 `JWT_SECRET` 环境变量，缺省值兼容现状
- `common` 依赖 `common-auth`；各服务继续使用原包名，不改调用点

**新增 `gateway-service`（端口 8088）**

- `gateway-service/pom.xml`：Spring Cloud Gateway，仅依赖 `common-auth`、Nacos discovery
- `GatewayApplication.java`、`application.yml`：先配置静态路由，白名单：
  - `/api/users/login`、`/api/users/register`、`/api/*/health`
  - `GET /api/activities/**`、`GET /api/news/**`、`GET /api/files/*/view`、`GET /api/files/*/download`
  - 其余（报名、考勤、群聊、AI、个人中心、上传）必须登录
- `config/JwtGlobalFilter.java`：
  - 校验 Bearer token
  - 删除客户端传入的 `X-User-Id/X-Username/X-User-Role`，按 token 重新注入
  - 统一 401 `{code:401,message,data:null}`
  - 透传 `Authorization`；AI 路由超时 300s
- `CorsConfig`：为 Taro H5 调试放行；小程序真机不受浏览器 CORS 限制
- `Dockerfile`、加入根 `pom.xml` modules 与 `docker-compose.yml`

**各服务补齐鉴权（纵深防御）**

- 把 `user-service/.../config/CustomHttpServletRequest.java` 提升到 `common`（或新建 `common-web`），提供统一请求包装：从 token 解析后注入 `X-User-Id` 头，供现有 `@RequestHeader` Controller 使用
- `activity-service/.../config/JwtAuthFilter.java`：删除全放行白名单，仅保留 `/health`；改用统一包装注入头
- `content/hr/monitor/project-award/ai` 新增 JwtAuthFilter 并注册；`file-service` 收紧白名单到 view/download/health
- 所有过滤器统一 401 JSON，不泄露异常细节

**Nginx**

- 把逐服务 `/api/*` location 收敛为单一 `location /api/ { proxy_pass http://gateway-service:8088; }`
- 保留 `/software-group/`、`/localstorage/`、静态资源回单体 WAR
- 旧路由注释保留作回滚

**验收**

- `mvn -pl common-auth,common,gateway-service -am package`
- curl 登录拿到 token
- 无 token 访问群聊返回 401
- 带伪造 `X-User-Id` 打受保护接口，服务端仍以 token 身份为准

### M2 content-service 真实实现（6–9 人日，最大工作量）

**真实 DAO（JdbcTemplate，SQL 可移植单体 `src/main/java/dao/*DAO.java`）**

- `GroupMessageDAO`：`findByGroupId(groupId, afterId, limit)`、`insert`、`findById`、`delete`
- `GroupMemberDAO`：成员校验、`last_read_at/last_read_message_id` 更新、未读计数
- `UserGroupDAO`、`ActivityGroupDAO`、`NewsDAO`（分页、按 type/status、详情）
- 需要时补 `UserDAO`/`MemberProfileDAO`/`FileStorageDAO` 的展示字段查询

**群聊接口改造**

- `GET /api/groups/mine`（token）：`[{groupId,groupName,ownerId,memberCount,unreadCount,lastMessage,lastMessageAt}]`
- `GET /api/groups/{id}/messages?afterId=&limit=`（token，校验成员身份）
- `POST /api/groups/{id}/messages`（token，body `{content}`，仅 TEXT，校验禁言）
- `POST /api/groups/{id}/read`（token，body `{messageId}`）
- 移除所有从 query/body 取 `userId` 的写法，改从请求上下文取

**新闻接口**

- `GET /api/news?type&page&pageSize`
- `GET /api/news/{id}` 返回 `contentHtml`
- 通知复用 `type=notice`

**数据迁移（增量）**

- `sql/migrations/20261028_mobile.sql`：`group_member` 加 `last_read_message_id INT NULL`，加索引 `idx_group_id_id (group_id, id)`
- 同步 `sql/software_group.sql`
- 执行 `python bin/convert_mysql_to_h2.py`；仅加列不需改 `H2Database.reset()` 表数组

**测试**

- H2 基座验证真实 SQL
- `afterId` 增量、未读游标、非成员拒绝、禁言拒绝

### M4 Taro 小程序（8–12 人日）

**脚手架与基础**

## 七、数据与配置变更

- 仅增量：`group_member.last_read_message_id` + 索引
- 迁移文件：`sql/migrations/20261028_mobile.sql`，同步主 schema 并重生成 H2
- 环境变量：`JWT_SECRET` 在 gateway 与所有服务保持一致；`MINIO_ENDPOINT` 保持内网；`DB_*` 沿用 compose

默认取舍（可推翻）：

1. 活动/新闻的 GET 公开，便于分享与首屏；报名、考勤、群聊、AI、个人中心必须登录
2. 文件 view/download 公开（图片可被 ID 枚举，首期接受；后续可换签名 URL）
3. 网关先静态 URI，避免 Nacos 启动顺序影响可用性，稳定后切 `lb://`
4. 群聊未读优先用 `last_read_message_id`，缺失时回退 `last_read_at`
5. AI 每日额度首期不做，仅记录会话归属

## 九、风险与回滚

| 风险 | 影响 | 应对 |
|---|---|---|
| content DAO 桩实现 | 群聊/新闻首期不可用 | M2 优先实装，H2 真实 SQL 测试 |
| 穿透域名无法做小程序合法域名 | 真机上线阻塞 | 开发用「不校验合法域名」；上线前准备备案域名 + HTTPS |
| 无 AppID | 真机/分享受限 | 测试号开发，AppID 到位后真机验收 |
| Gateway WebFlux 与 common spring-web 冲突 | 启动失败 | 拆 `common-auth`，Gateway 不依赖 `common` |
| 密钥硬编码/轮换 | token 全部失效 | 统一 `JWT_SECRET` 并集中配置，轮换前通知 |
| 服务端口直连绕过网关 | 越权 | 各服务补 JwtAuthFilter，做纵深防御 |
| Nginx 路由切换故障 | PC/App 全挂 | 保留旧 location 注释，秒级回滚 |
