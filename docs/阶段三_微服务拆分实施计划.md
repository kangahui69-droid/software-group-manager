## 一、背景与目标

### 1.1 背景

阶段二已成功完成中间件引入（Redis、RabbitMQ、Nginx），验证了环境一致性和数据持久化。

**阶段二完成后的现状**：
- 单体 WAR 应用运行在 Tomcat 9 容器内
- Redis 已用于缓存热点数据和 Session 共享
- RabbitMQ 已配置（AI 消息异步处理待完成）
- Nginx 已配置反向代理和静态资源服务
- 所有服务通过 Docker Compose 编排

**阶段三目标**：
将单体 WAR 拆分为多个独立部署的微服务，引入 Spring Cloud 生态（Nacos、Sentinel、Feign）实现服务治理。

### 1.2 目标

1. **服务拆分**：将 15 个 Service 合并拆分为 9 个独立微服务
2. **服务注册与发现**：引入 Nacos 作为服务注册中心（配置管理延用本地 application.yml）
3. **API 路由**：延用阶段二 Nginx 实现路由分流（/api/* → 微服务，其他 → 旧 WAR）
4. **服务通信**：引入 OpenFeign 实现同步服务间通信
5. **熔断器**：引入 Sentinel 实现服务容错
6. **部署方式**：新服务使用 Spring Boot JAR 部署，旧 WAR 保留不变
7. **数据库隔离**：共享 Schema + MySQL 用户权限实现表级隔离
8. **前端策略**：旧 WAR 保留 JSP 渲染不动，新旧系统通过 Nginx 路由并行运行

### 1.3 关键技术选型（修正版）

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 框架选择 | Spring Boot 3.2.x | **升级**：需要 Java 17，但获得更长维护周期和原生响应式支持 |
| Java 版本 | Java 17 | **升级**：Spring Boot 3.x 要求 Java 17+，且大多数第三方库已支持 |
| 服务通信 | OpenFeign | 声明式 HTTP 客户端，代码侵入性小 |
| 服务注册 | Nacos 2.2.3 | **仅用服务发现**，配置管理延用本地 application.yml（降低复杂度） |
| API 网关 | **不使用**（延用阶段二 Nginx） | 1-2人团队不需要额外网关层；Nginx 已配置反向代理、静态资源、SSE |
| 熔断器 | Sentinel 1.8.6 | 阿里开源，功能完善，Nacos 集成好 |
| 数据库策略 | **共享 Schema + DB用户权限隔离** | 避免大规模 ALTER TABLE 风险，通过 MySQL GRANT 实现表级隔离 |
| JWT 策略 | JJWT + Redis 黑名单 | 无状态认证 + 主动失效 |
| 文件存储 | MinIO 对象存储 | 替代本地文件系统共享问题，支持 S3 协议 |
| 分布式事务 | RabbitMQ 最终一致性 | **延用阶段二已有 RabbitMQ**，避免引入新组件 |

**修正后的拆分顺序（采用合并方案）**：

```

  ✅ file-service — 所有需要文件存储的服务都依赖它，必须最先拆分

  ⚠️ user-service — 依赖 FileStorageDAO（用于头像上传）

第三梯队（无外部依赖，可独立拆分）：
  ✅ activity-service — 合并 Activity + Attendance + Study
  ✅ hr-service — 合并 Recruit + Resume
  ✅ monitor-service — 合并 Problem + Log

第四梯队（依赖第二梯队，通过 Feign 调用 file-service）：
  ⚠️ project-award-service — 合并 Project + Award（业务强关联）
  ⚠️ content-service — 合并 Group + News

最后（特殊处理）：
  🔴 ai-service — 混合模式（AI自身表直连DB，业务数据走Feign），独立部署
```

**服务数量**：9 个业务服务（合并后从 13→9），**不再单独部署 jsp-bff 和 gateway**。

**架构简化决策**：
1. **不做 jsp-bff**：旧 WAR 保留不动，Nginx 按路径分流（/api/*→微服务，其他→旧WAR），渐进替换
2. **不做 Spring Cloud Gateway**：Nginx（阶段二已配置）继续承担反向代理、静态资源、SSE
3. **合并相关服务**：减少服务数量（详见 5.4 节）
4. **分批上线**：第一批只拆 file-service + user-service + activity-service（3个），验证架构后再推进

#### 1.4.1 AIService 特殊处理方案

**问题**：AIService 直接依赖 15 个 DAO，是典型的聚合服务（Anti-pattern for microservices）。

**解决方案**：采用 **混合模式**——AI 自身数据直连，业务数据走 Feign + Redis 缓存。

```
┌─────────────────────────────────────────────────────────────────┐
│                      AI Service 混合模式                          │
├─────────────────────────────────────────────────────────────────┤
│                                                                   │
│   ┌─────────┐     ┌─────────┐     ┌──────────────┐              │
│   │  旧WAR  │────▶│  Nginx  │────▶│ AI Service   │              │
│   │  (JSP)  │     │  (80)   │     │  (混合模式)   │              │
│   └─────────┘     └─────────┘     └──────┬───────┘              │
│                                       │                          │
│         ┌─────────────────────────────┼─────────────────────┐   │
│         │   AI 自身表（直连 DB）       │  业务数据（Feign）    │   │
│         │  ┌────────┐  ┌────────┐    │  ┌────────┐          │   │
│         │  │AIConv- │  │AIMsg   │    │  │User    │          │   │
│         │  │ersation│  │Status  │    │  │Feign   │          │   │
│         │  │DAO     │  │DAO     │    │  │Client  │          │   │
│         │  └────────┘  └────────┘    │  └────────┘          │   │
│         │  ┌────────┐  ┌────────┐    │  ┌────────┐          │   │
│         │  │AIKnow- │  │AIFaq   │    │  │Activity│          │   │
│         │  │ledge   │  │Stats   │    │  │Feign   │          │   │
│         │  │DAO     │  │DAO     │    │  │Client  │          │   │
│         │  └────────┘  └────────┘    │  └────────┘          │   │
│         └─────────────────────────────┴─────────────────────┘   │
│                                                                   │
└─────────────────────────────────────────────────────────────────┘
```

**两条数据路径**：

| 路径 | 适用数据 | 方式 | 理由 |
|------|---------|------|------|
| **直连 DB** | AI 自身表（ai_conversation, ai_message, ai_knowledge_base 等） | JDBC/JdbcTemplate | 无跨服务依赖，简单高效 |
| **Feign + Redis 缓存** | 业务数据（用户信息、活动列表、项目等） | Feign 调用 + Spring Cache | 解耦业务服务，缓存减少调用 |

**代码示例**：

```java
// ✅ 混合模式：自身数据直连，业务数据走 Feign
@Service
public class AIService {
    // AI 自身表 DAO（直连）
    private final AIConversationDAO conversationDAO;
    private final AIMessageDAO messageDAO;
    private final AIKnowledgeBaseDAO knowledgeDAO;

    // 业务数据通过 Feign 获取（带缓存降级）
    private final UserFeignClient userFeignClient;
    private final ActivityFeignClient activityFeignClient;

    // 热点数据使用 Redis 缓存，减少 Feign 调用
    @Cacheable(value = "userInfo", key = "#userId")
    public UserDTO getUserInfo(Integer userId) {
        Result result = userFeignClient.getUserById(userId);
        return result.isSuccess() ? (UserDTO) result.getData() : null;
    }
}
```

**⚠️ 明确禁止**：AI Service **不得**通过 JdbcTemplate 直接跨表查询业务数据（如 `SELECT * FROM activity` 等）。这会导致：
- Schema 绑定过紧，业务表结构变更会级联影响 AI 服务
- 绕过微服务隔离边界，退化为"分布式的单体"

### 1.5 不做的事（范围控制）

- 不做 Kubernetes 部署（阶段四内容）
- 不做 CI/CD 流水线（阶段四内容）
- 不做 Spring Cloud Gateway（延用阶段二 Nginx，阶段四再评估）
- 不做 Seata 分布式事务（延用阶段二 RabbitMQ 最终一致性，阶段四再评估）
- 不做服务网格（Istio/Linkerd）
- 不做表前缀迁移（风险太高，改为共享 Schema + DB用户权限隔离）
- **不做 jsp-bff 服务**（旧 WAR 保留不动，Nginx 路由分流，渐进替换）
- **common 模块仅包含最小共享代码**：Result.java、JwtUtil.java、BaseException（不含 DAO，避免耦合）

### 1.6 javax.servlet → jakarta.servlet 迁移（重要）

**⚠️ 这是阶段三最容易被低估的工作量**

当前项目使用 `javax.servlet.*`（Servlet 4.0 / Java EE 8），而 **Spring Boot 3.x 要求 `jakarta.servlet.*`**（Jakarta EE 9+）。

**影响范围统计**（2026-08-02 实际 grep 结果）：
- **src/main/java**：~200 处
- **src/test/java**：~116 处
- **总计约 316 处** javax.servlet 引用，分布在 76 个文件中
- **web.xml**（16KB）：所有 `<filter-class>`、`<listener-class>` 配置需更新
- **测试基础设施**：EmbeddedTomcat.java 需从 Tomcat 9（javax）升级到 Tomcat 10+（jakarta）

**修改内容**：
```java
// 修改前（javax.servlet）
import javax.servlet.ServletException;
import javax.servlet.http.HttpServlet;
import javax.servlet.http.HttpServletRequest;
import javax.servlet.http.HttpServletResponse;

// 修改后（jakarta.servlet）
import jakarta.servlet.ServletException;
import jakarta.servlet.http.HttpServlet;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
```

**涉及的文件类型**：
| 类型 | 数量 | 说明 |
|------|------|------|
| Servlet | ~31 个 | 继承 `HttpServlet`，需要改为继承 `jakarta.servlet.http.HttpServlet` |
| API Servlet | 14 个 | 继承 `BaseApiServlet`，同样需要迁移 |
| Filter | 5 个 | 实现 `Filter` 接口 |
| Listener | 2 个 | 实现 `ServletContextListener` 等 |

**迁移策略**：
1. **使用 IDE 批量替换**（推荐）
   - IntelliJ IDEA: `Ctrl + Shift + R` → 替换 `javax.servlet` → `jakarta.servlet`
   - 注意：只替换 import 语句，不要替换包名

2. **验证方法**：
   ```bash
   # 检查是否还有 javax.servlet 残留
   grep -r "import javax.servlet" src/main/java/
   # 应该返回空结果
   ```

3. **额外检查**：
   - `web.xml` 中的 `<filter-class>` 等配置（如果使用传统配置）
   - 第三方库可能仍使用 `javax.servlet`（需要检查兼容性）

**工期影响**：**增加 4-6 周** 用于 javax→jakarta 迁移和调试（含测试基础设施升级）

**⚠️ 额外风险（容易被忽略）**：

1. **第三方库兼容性**：以下库需要逐个验证 jakarta 兼容性：
   | 库 | 当前版本 | 风险 | 验证方法 |
   |------|---------|------|---------|
   | HikariCP | 4.0.3 | 低（纯JDBC，不依赖Servlet） | 编译通过即可 |
   | Jackson | 2.16.0 | 低（通用库） | 编译通过即可 |
   | Jsoup | 1.17.2 | 低（HTML解析） | 编译通过即可 |
   | Jedis | 5.1.0 | 低（Redis客户端） | 编译通过即可 |
   | RabbitMQ AMQP | 5.20.0 | 低（消息队列客户端） | 编译通过即可 |
   | Apache HttpClient | 4.5.14 | 低（HTTP客户端） | 编译通过即可 |
   | **Hibernate Validator** | （需确认） | **中** | 验证是否依赖 javax.validation |
   | **AI SDK（minimax/volcengine）** | （需确认） | **高** | 检查 SDK 是否引用 javax.servlet |
2. **web.xml 配置**：`<filter-class>`、`<listener-class>` 等配置也需要修改
3. **测试代码**：`src/test/java` 中 ~116 处引用也需要迁移
4. **EmbeddedTomcat**：测试基类使用的 Tomcat 9 不支持 jakarta，需升级到 Tomcat 10+

**建议执行步骤**：
```bash

mvn clean compile 2>&1 | grep -i "cannot find symbol"

# 4. 逐个解决第三方库问题（可能需要升级版本或寻找替代库）

# 5. 运行测试，确保功能正常
mvn test

# 6. 如果失败，准备回滚方案
git checkout main
```

### 3.0 前置准备 `[已完成]`

#### 3.0.1 JSP Session 依赖清查 `[已完成]`

**目的**：确认旧 WAR 中所有依赖 `session.getAttribute` 的页面，为 JWT 迁移做准备。

**执行结果**：

| 项目 | 数量 |
|-----|------|
| 涉及JSP | 10个（**全部需要修改**） |
| 涉及Servlet | 21个 |
| session引用总数 | **130+处** |

**Session Attribute 汇总**：

| 属性 | 设置位置 | 读取位置 | 迁移方案 |
|-----|--------|---------|---------|
| `user` | LoginServlet | 全部Servlet+JSP+Filter | → JWT Token |
| `username` | LoginServlet | 仅LogoutServlet | 从user对象获取 |
| `role` | LoginServlet | AuthHelper | 从user.getRole() |
| `memberProfile` | ProfileServlet, JSP | member/* JSP | → user-service API |
| `adminProfile` | AdminServlet | admin/* JSP | → user-service API |
| `aiSessionId` | AIServlet | AIServlet | → ai-service内部 |
| `CSRF_TOKEN` | CSRFTokenServlet | 仅内部 | 移除（JWT防CSRF） |

**关键修改点**：
1. **LoginServlet** — 登录从设置session改为返回JWT token
2. **AuthHelper** — 从基于session改为基于JWT解析
3. **10个JSP** — `session.getAttribute("user/profile")` 改为调用user-service API
4. **2个Filter** — AuthFilter拆分为各微服务的JWT Filter

**详细报告**：[阶段三_Session依赖清查报告.md](./阶段三_Session依赖清查报告.md)

#### 3.0.2 RegistrationDAO 与 ActivityParticipantDAO 合并 `[已完成]`

**问题**：两个 DAO 操作同一张表 `activity_participant`，功能重叠约 60%。

| DAO | 行数 | 方法数 | 定位 |

#### ⚠️ 重要：DES密钥一致性

**问题描述**：2026-08-03 发现 DES 加密密钥配置错误，导致登录时密码验证失败。

**根本原因**：

### 3.9 Nginx 路由配置（新旧系统并行）`[已完成]`

**策略**：放弃 jsp-bff 方案（Spring Boot JAR 不支持 JSP，Feign 与 Servlet 难以共存）。改为**保留旧 WAR 不动 + Nginx 按路径分流**。

```
┌─────────────────────────────────────────────────────────────────────┐
│              旧 WAR + 新微服务 并行架构（过渡期）                      │
├─────────────────────────────────────────────────────────────────────┤
│                                                                      │
│   浏览器 ──▶ Nginx (:80) ──┬── /api/files/**  → file-service       │
│                             ├── /api/users/**  → user-service       │
│                             ├── /api/activities/** → activity-svc   │
│                             ├── /api/ai/**     → ai-service         │
│                             └── 其他所有路径    → 旧 WAR (:8080)     │
│                                                                      │
│   旧 WAR 继续提供：JSP 页面渲染、Session 登录、未拆分的业务功能       │
│                                                                      │
└─────────────────────────────────────────────────────────────────────┘
```

**Nginx 配置更新**（在阶段二 `nginx/nginx.conf` 基础上增加微服务路由）：

```nginx
# === 新增：微服务 API 路由 ===
# file-service
location /api/files/ {
    proxy_pass http://file-service:8081;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-User-Id $http_x_user_id;     # JWT 解析后的用户ID
    proxy_set_header X-User-Role $http_x_user_role;  # JWT 解析后的角色
}

# user-service
location /api/users/ {
    proxy_pass http://user-service:8082;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
}

# activity-service
location /api/activities/ {
    proxy_pass http://activity-service:8084;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
}

# ai-service
location /api/ai/ {
    proxy_pass http://ai-service:8094;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    # SSE 支持（阶段二已配置）
    proxy_buffering off;
    proxy_read_timeout 300s;
}

# === 兜底：所有其他请求 → 旧 WAR ===
location / {
    proxy_pass http://app-legacy:8080;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
}
```

**关键说明**：
1. **旧 WAR 不做任何改造**：保留 Session 认证、JSP 渲染、所有未拆分的业务
2. **微服务 API 使用 JWT 认证**：Gateway 路由层不验证（延用阶段二的 Nginx 配置），由各微服务自行验证 JWT
3. **渐进替换**：每拆分一个新服务，就在 Nginx 中增加一条 location 规则
4. **不需要 jsp-bff 服务**：旧 WAR 本身就是 JSP 渲染器

**优势**：
1. 零风险：旧 WAR 原封不动，新服务独立上线
2. 回滚简单：删除 Nginx 中对应 location 即可切回旧 WAR
3. 不需要重写前端页面
4. 不需要解决 Servlet+Feign 共存问题

## 五、数据库策略详解

### 5.1 为什么放弃 Schema 隔离方案

**问题**：MySQL 跨 Schema 无法使用 FK 约束。

原项目 20+ 张表 FK 指向 `user` 表：
```sql
-- 无法跨 Schema 约束
activity.creator_id -> user.id  -- user 在 user_schema
project.leader_id -> user.id    -- user 在 user_schema
```

### 5.2 修正后的方案：共享 Schema（无表前缀）+ DB 用户权限隔离

**原因**：表前缀迁移需要 44 次 ALTER TABLE，每次都可能锁表，风险极高。

**新方案**：
- 所有服务共享同一个 Schema（同 `software_group`）
- 每个微服务使用**独立的 MySQL 用户**，通过 GRANT 限制可访问的表
- 这提供了**机制级**（而非仅约定级）的隔离

**DB 用户创建脚本**（在 3.1 基础设施搭建时执行）：

```sql
-- 创建各服务专用 DB 用户
CREATE USER IF NOT EXISTS 'file_svc'@'%' IDENTIFIED BY 'file_svc_pass';
CREATE USER IF NOT EXISTS 'user_svc'@'%' IDENTIFIED BY 'user_svc_pass';
CREATE USER IF NOT EXISTS 'activity_svc'@'%' IDENTIFIED BY 'activity_svc_pass';
CREATE USER IF NOT EXISTS 'content_svc'@'%' IDENTIFIED BY 'content_svc_pass';
CREATE USER IF NOT EXISTS 'project_award_svc'@'%' IDENTIFIED BY 'pa_svc_pass';
CREATE USER IF NOT EXISTS 'hr_svc'@'%' IDENTIFIED BY 'hr_svc_pass';
CREATE USER IF NOT EXISTS 'monitor_svc'@'%' IDENTIFIED BY 'monitor_svc_pass';
CREATE USER IF NOT EXISTS 'ai_svc'@'%' IDENTIFIED BY 'ai_svc_pass';
-- 旧 WAR 继续使用 root 或独立用户

-- file-service: 只访问文件相关表
GRANT SELECT, INSERT, UPDATE, DELETE ON software_group.file_storage TO 'file_svc'@'%';

-- user-service: 只访问用户相关表
GRANT SELECT, INSERT, UPDATE, DELETE ON software_group.user TO 'user_svc'@'%';
GRANT SELECT, INSERT, UPDATE, DELETE ON software_group.member_profile TO 'user_svc'@'%';
GRANT SELECT, INSERT, UPDATE, DELETE ON software_group.admin_profile TO 'user_svc'@'%';
GRANT SELECT, INSERT, UPDATE, DELETE ON software_group.user_group TO 'user_svc'@'%';

-- activity-service: 只访问活动相关表
GRANT SELECT, INSERT, UPDATE, DELETE ON software_group.activity TO 'activity_svc'@'%';
GRANT SELECT, INSERT, UPDATE, DELETE ON software_group.activity_participant TO 'activity_svc'@'%';
GRANT SELECT, INSERT, UPDATE, DELETE ON software_group.activity_group TO 'activity_svc'@'%';
GRANT SELECT, INSERT, UPDATE, DELETE ON software_group.attendance TO 'activity_svc'@'%';
GRANT SELECT, INSERT, UPDATE, DELETE ON software_group.attendance_makeup TO 'activity_svc'@'%';
GRANT SELECT, INSERT, UPDATE, DELETE ON software_group.attendance_config TO 'activity_svc'@'%';
GRANT SELECT, INSERT, UPDATE, DELETE ON software_group.study_session TO 'activity_svc'@'%';

-- ... 其他服务类似，按实际需要授权的表执行 GRANT

FLUSH PRIVILEGES;
```

**各服务 application.yml 中使用自己的 DB 用户**：
```yaml
spring:
  datasource:
    username: ${DB_USER:-file_svc}
    password: ${DB_PASSWORD:-file_svc_pass}
```

**优势**：
- 无需数据迁移、FK 约束仍然有效、运维简单
- **真实隔离**：user-service 即使写错 SQL 也无法访问 activity 表（MySQL 会拒绝）
- 符合"最小权限"原则

**代码审查**：仍然禁止跨服务直接访问对方表（通过 Feign 调用），DB 权限是**保底机制**。

### 5.5 数据库连接池管理

**问题**：共享 Schema 模式下，9 个服务 × 10 连接 = 90 连接（+ 旧 WAR + Nacos 等）。

**解决方案**：

```yaml
# 每个服务的 application.yml 限制连接池
spring:
  datasource:
    hikari:
      maximum-pool-size: 10
      minimum-idle: 2
      connection-timeout: 30000
      idle-timeout: 600000
      max-lifetime: 1800000
```

**MySQL 连接数估算**（合并后）：
- 9 个微服务 × 10 最大连接 = 90
- 旧 WAR 连接池 ≈ 10
- Nacos（连 MySQL）≈ 5
- MySQL 自身连接 ≈ 5
- **总计 ≈ 110**
- **MySQL max_connections 建议设置为 200**（留有余量）

> 相比原 15 服务方案的 150+ 连接，合并后减少了约 30%。

### 5.3 分布式事务策略

**阶段三不使用 Seata**。Seata 推迟至阶段四评估。

推荐方案（按复杂度排序）：

#### 方案A：同步 Feign + 本地事务（最简单，推荐首选）

将跨服务操作封装在一个服务内完成，不跨服务则无需分布式事务：

```java
public Result createProjectWithMember(ProjectDTO dto, Integer userId) {
    // 全部在 project-award-service 内完成，一个本地事务搞定
    Connection conn = getConnection();
    try {
        conn.setAutoCommit(false);
        projectDAO.insert(dto);
        projectMemberDAO.addMember(projectId, userId);
        conn.commit();
    } catch (Exception e) {
        conn.rollback();
    }
}
```

#### 方案B：RabbitMQ 最终一致性（需要跨服务时使用）

利用阶段二已配置的 RabbitMQ 做异步数据同步：

```java
// 发送方
rabbitTemplate.convertAndSend("project.events", "project.created", event);

// 消费方
@RabbitListener(queues = "project.created")
public void handleProjectCreated(ProjectCreatedEvent event) {
    // 有失败重试机制，保证最终一致
}
```

#### 方案C：Seata（阶段四评估）

只有当方案A和B都无法满足且业务确实需要强一致性补偿时才考虑。阶段三不引入。
